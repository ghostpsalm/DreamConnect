  symlink, guarded by the same `valid_home_dir "$target_home"` check as the neighboring
  unit-file removal (install.sh ~95-99), placed BEFORE it (reverse of install order:

root cause (confirmed by reading install.sh): `systemctl --user disable --now
dreamconnect-daemon.service` (line 87) bundles a live stop into the call via `--now`,
which needs a reachable bus. When the host account's user manager isn't up (never
initialized, or box rebooted since last login), the WHOLE invocation errors (not a
partial no-op) and `2>/dev/null || true` swallows it -- so the on-disk enablement
symlink is never removed, dangling after the unit file itself is deleted a few lines
later. `daemon-reload` (line 100) has no on-disk artifact of its own, so its `|| true`
is genuinely harmless -- only `disable`'s failure matters.

owner-confirmed design decision: NOT a bus-reachability wait (mirroring #24) -- a
host account that never had a session will never bring its bus up, so waiting would
just burn the timeout for nothing. Instead, remove the symlink directly and
unconditionally, independent of whether the live systemctl call succeeded.

## Reviewer/breaker follow-ups (non-blocking per reviewer's own verdict; NOT filed as GitHub issues -- token lacks issues:write scope, same limitation as issues #22/#25/#26)

1. **The new test's dynamic WantedBy= derivation defends against a CHANGED target but not an ADDED one.** It takes the first token of the first `WantedBy=` line and stops -- if a future edit adds a second `WantedBy=` (e.g. also `default.target`), `systemctl enable` would create two symlinks, uninstall() would only remove one, and the suite would stay green while #28 recurs under the new target. Low priority: single-target is the current and likely permanent shape.
2. **Pre-existing, not introduced by this diff** (breaker + reviewer agree): both the new `rm -f` and its pre-existing sibling (the unit-file removal) run under `set -euo pipefail` with no `\|\| true`, and `valid_home_dir` is a pure string predicate with no filesystem check. If any path component under `$target_home` were a symlink pointing elsewhere, or a directory occupied the target path, `rm -f` could follow a symlink outside the intended directory as root, or fail non-zero (EISDIR on a directory) and abort the rest of uninstall() -- SC drop-in revert, autologin revert, account deletion, state cleanup all left undone -- with no `\|\| true` to catch it. Requires external tampering or write access to the account's own home directory. Worth noting the block's own comment states the opposite intent ("skipped rather than fatal ... everything after this line still needs reverted"), so this is a real gap in an existing convention, not this diff's to fix.
3. **Cosmetic**: the now-empty `graphical-session.target.wants/` directory is left behind (the sibling drop-in cleanup elsewhere in this function does `rmdir ... \|\| true`). Inert, no failure scenario.
