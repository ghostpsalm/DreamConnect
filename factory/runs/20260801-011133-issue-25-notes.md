# In progress: issue #25 — userdel races a lingering user manager on --uninstall
branch: install/host-account-fixes-2   worktree: /home/kogies/.factory/worktrees/dreamconnect/host-account-fixes-2   started: 2026-07-31T23:31:54Z
seams:
- install-lib.sh :: new function wait_for_user_manager_down(uid, [timeout_seconds]) —
  the mirror of this same file's existing wait_for_user_bus (#24): polls
  `systemctl is-active user@<uid>.service` until it reports inactive/failed/not-found,
  reusing wait_for_user_bus's exact timeout-validation guard. DC_DRY_RUN=1 short-
  circuits before ever invoking systemctl.
  CLARIFIED WITH OWNER (oracle-found gap): `systemctl is-active` reports `deactivating`
  with the SAME non-zero exit code as `inactive`/`failed` for a unit still mid-shutdown
  with a live MainPID -- exactly the process userdel races. "Down" is NOT "any non-zero
  exit"; the poll must specifically check for `inactive`/`failed` STRING output (or
  unit-not-found), and keep polling while the state string reads `deactivating`
  (or `active`/`activating`). Getting this wrong reopens issue #25 exactly.
- install-lib.sh :: uninstall_host_account — wire the wait in between
  `loginctl terminate-user` and `userdel -r`. On timeout: non-fatal, skip userdel,
  return non-zero (matches the function's existing left-in-place-for-retry
  behavior; NOT a hard `die` — confirmed with owner, differs from wait_for_user_bus's
  install-side `|| die` because teardown shouldn't abort an already-in-progress
  uninstall).
- install-lib.sh :: remove_no_idle_lock — also remove the compiled dconf db
  (`$dir/db/$name`, no `.d` suffix) once its source directory (`$dir/db/$name.d`)
  is removed outright (the "we own this outright" branch, no backup keyfile being
  restored) — verified empirically that `dconf update` never regenerates or cleans
  up a stale compiled db once its source .d directory is gone. When a backup IS
  being restored (reused pre-existing account), leave the compiled db alone;
  `dconf update` regenerates it from the restored source.

root cause (confirmed by reading install-lib.sh): uninstall_host_account already
runs disable-linger -> terminate-user -> userdel in the right ORDER, but
terminate-user is asynchronous — it signals systemd and returns before the
account's processes/manager have actually exited — so userdel -r can still race
a live process and fail ("user X is currently used by process N"), leaving the
account, its home, and a stale compiled dconf db orphaned. Second, independent
finding: remove_no_idle_lock's dconf cleanup deletes the source .d directory but
never the compiled binary db dconf produced from it, which dconf update then
never cleans up.

owner-confirmed design decision: wait_for_user_manager_down's timeout is
NON-FATAL — skip userdel, return non-zero, leave the account for a retry —
not a hard abort, differing deliberately from wait_for_user_bus's install-side
`|| die`.

gate: ./run-tests.sh (Java boot tests -> Python daemon tests -> bash test_install.sh).
No scripts/gate.sh in this repo.

## Reviewer follow-ups (non-blocking per reviewer's own verdict; NOT filed as GitHub issues -- token lacks issues:write scope, same limitation as issues #22/#26)

1. **The wait keys on install.state's RECORDED uid, userdel keys on the account NAME.** If the account is removed and recreated by hand (or `usermod -u`'d) between install and uninstall, `systemctl is-active user@<stale-uid>.service` can answer `inactive` immediately (the OLD uid's manager really is down) while the NEW manager for that name is still live -- the wait returns 0 instantly and userdel races it, reopening issue #25 silently. Reviewer's suggested fix: derive uid from `passwd_entry "$name"` (already read by `uninstall_host_account`/`host_account_removable`) instead of a 3rd argument sourced from install.state -- would also have avoided the 3-arg signature change and the 6-call-site test churn entirely. Not fixed here: a genuine redesign of already-tested work, not a small patch: filing rather than reworking mid-review.
2. **Empty `systemctl` output (not just a malformed uid) also burns the full timeout.** A valid uid with a `systemctl` that can't answer at all (absent from PATH, non-booted systemd in a container) prints nothing on stdout; no `case` arm matches; 30s burns; userdel is skipped. Empty stdout is evidence we couldn't ask, not evidence the manager is up.
3. **The timeout-validation guard is now duplicated verbatim between `wait_for_user_bus` and `wait_for_user_manager_down`** (same drift-risk class the earlier `disable_autologin` regex duplication caused in issue #22). Suggest extracting one shared validator.
4. **`wait_for_user_bus` (pre-existing, issue #24, untouched by this diff) lacks the uid-validation guard `wait_for_user_manager_down` just gained**, despite being explicitly modeled on it. Reviewer agreed with the breaker's risk assessment (its uid is live from `resolve_host_identity` in the same run, worst case is a 30s stall then a loud `|| die`, not a silent skip) -- not a blocker, but a parity gap worth closing alongside #3's shared-validator extraction.
5. **`install.sh --uninstall` exits 0 even after a failed account removal** (pre-existing behavior, not introduced by this diff) -- unattended callers can't detect a partial uninstall from the exit code alone, only from stderr text.
