# Hazards — DreamConnect (fragment: issue #26, push/unpush DCONF_PROFILE)

Read by the `breaker` before every red team; appended by `/submit`. Not a bug list — the issue tracker
holds work. This holds *where trouble has been found before, and what has already been ruled out*.

A rule-out is evidence only while the code it names is unchanged, which is why every row carries a path
and the commit it was established at. Expiry is checked with **both** `git log <commit>..HEAD -- <path>`
and `git diff HEAD -- <path>` — a red team works on an uncommitted tree, so `git log` alone cannot see
the change it is there to attack.

## Held — found once, now guarded by a test

| hazard | path | test that holds it | commit |
|---|---|---|---|
| `--uninstall` never cleared `DCONF_PROFILE` from a reused account's live `systemd --user` manager; `remove_no_idle_lock` deleted the profile file the variable still named, dropping dconf to its null configuration and costing that account every gsettings read/write until logout | `install-lib.sh :: unpush_dconf_environment` (new), `install.sh :: uninstall()` | `test_unpush_dconf_environment_unsets_the_profile_from_the_running_manager`, `test_install_sh_unpushes_dconf_environment_on_uninstall` | bb0123d |
| The unpush call was ordered after `loginctl disable-linger` — the only thing that stops a reused account's manager (`CREATED_ACCOUNT=0`, so `uninstall_host_account`'s `terminate-user` never runs) — making it a no-op (or a race against a dying manager) in the exact case it was meant to fix | `install.sh :: uninstall()` | `test_install_sh_unpushes_dconf_environment_before_disabling_linger` | bb0123d |
| `push_dconf_environment`/`unpush_dconf_environment` bypassed `run()`, so `DC_DRY_RUN=1` did not actually prevent them invoking `sudo`/`systemctl` — the only two state-mutating install-lib.sh calls with that gap | `install-lib.sh :: push_dconf_environment`, `:: unpush_dconf_environment` | `test_push_and_unpush_dconf_environment_gate_the_invocation_behind_run` | bb0123d |

## Ruled out — probed with evidence, no defect found

| hypothesis | path | evidence | established at |
|---|---|---|---|
| `uid` argument to `push_dconf_environment`/`unpush_dconf_environment` is unvalidated and could be attacker/misconfiguration-controlled in a way that matters (e.g. a corrupted `install.state` handing it a bad/empty/root uid) | `install-lib.sh :: push_dconf_environment`, `:: unpush_dconf_environment` | `sudo -u "$name"` drops privilege before `/run/user/$uid` is ever touched; `/run/user/<uid>` is `0700`, so a wrong or empty uid fails closed (`No such file or directory` / `Operation not permitted`), caught by the non-fatal `\|\|`. Same exposure already exists at install.sh:84 for the pre-existing `target_run_user` construction — not new | bb0123d |
| Calling `unpush_dconf_environment` (a `sudo -u <name>` invocation) inside `uninstall()` could re-spawn a logind session for `<name>` that then blocks the later `userdel` | `install-lib.sh`, `install.sh :: uninstall()` | `uninstall_host_account` (install-lib.sh) runs its own `disable-linger` + `terminate-user` immediately before `userdel -r`; traced end to end, no ordering hazard | bb0123d |
| A mutant hardcoding the literal account name/uid instead of reading `$1`/`$2` in `push_dconf_environment` could still pass the suite | `install-lib.sh :: push_dconf_environment` | `test_push_dconf_environment_invokes_set_environment_with_the_profile_name` now exercises two distinct (name, uid) pairs with no shared substrings; the mutant fails on the second pair | bb0123d |
| A mutant removing the `valid_account_name` half of the guard (leaving only the `root\|user\|local` case) could still pass the suite | `install-lib.sh :: push_dconf_environment`, `:: unpush_dconf_environment` | `test_push_dconf_environment_refuses_malformed_account_names`, `test_unpush_dconf_environment_refuses_reserved_and_malformed_names` cover `./user`, `..`, `.`, an all-numeric name, and a name containing a space — all fail the mutant | bb0123d |

## Unprobed — no oracle available
