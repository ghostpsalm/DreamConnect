# Hazards — DreamConnect (fragment: issue #18, display-host account)

Read by the `breaker` before every red team; appended by `/submit`. Not a bug list — the issue tracker
holds work. This holds *where trouble has been found before, and what has already been ruled out*.

A rule-out is evidence only while the code it names is unchanged, which is why every row carries a path
and the commit it was established at. Expiry is checked with **both** `git log <commit>..HEAD -- <path>`
and `git diff HEAD -- <path>` — a red team works on an uncommitted tree, so `git log` alone cannot see
the change it is there to attack.

## Ruled out — probed with evidence, no defect found

| hypothesis | path | evidence | established at |
|---|---|---|---|
| `passwd_entry`/`resolve_host_identity`'s `awk '$1==n'` fixture lookup is prefix-vulnerable (`dchost` vs `dchost2`) | `install-lib.sh::passwd_entry`, `::resolve_host_identity` | Exact-match test with `dreamconnect-host2` deliberately placed before `dreamconnect-host` in the fixture; independently re-verified by two separate breaker passes | f08b3ff |
| `read_install_state` is vulnerable to a hostile/malformed state file via `source`/`eval` | `install-lib.sh::read_install_state` | Confirmed line-by-line `case`-statement parse, no `source`/`.`/`eval` anywhere in the file (`grep`); duplicate keys last-wins; lines without `=` ignored; all four keys reset on every call regardless of file presence | f08b3ff |
| A hostile `HOST_ACCOUNT` value achieves shell injection through any consumer | `install.sh` (multiple call sites), `install-lib.sh` (multiple functions) | Every consumer quotes the variable; `HOST_ACCOUNT='; rm -rf /'`-style payloads are inert. `valid_account_name`'s character-class guard closes the path-traversal variant separately (see Held) | f08b3ff |
| `ensure_host_account` mutates the GECOS or password of a pre-existing (not newly-created) account | `install-lib.sh::ensure_host_account` | Code path for an existing account (`passwd_entry` returns non-empty) skips both `useradd` and `usermod` entirely — confirmed by direct read plus the "skips useradd when the account exists" test | f08b3ff |
| Two concurrent `install.sh` runs with the *same* `DREAMCONNECT_HOST_ACCOUNT` corrupt state or double-create | `install-lib.sh::ensure_host_account`, `install.sh` | The loser's `useradd` fails under `set -e` before `write_install_state` ever runs — no corruption, just a loud abort. (Concurrent runs with *different* names is a real, separate gap — filed as issue #21, not re-probed here since it's tracked.) | f08b3ff |
| Restoring a keyfile backup into `<name>.d/` and then attempting `rmdir` on that directory could delete the just-restored file or leave a plain file where a directory belongs | `install-lib.sh::remove_no_idle_lock` | Restore (`mkdir -p` + `mv`) runs strictly before the `rmdir` attempt; directory is non-empty afterward so `rmdir` fails harmlessly. Mutation-tested: hoisting `rmdir` above the restore was independently confirmed to corrupt the directory into a plain file | f08b3ff |
