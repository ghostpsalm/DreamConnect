# Hazards — DreamConnect (fragment: issue #25, userdel/lingering-manager race)

Read by the `breaker` before every red team; appended by `/submit`. Not a bug list — the issue tracker
holds work. This holds *where trouble has been found before, and what has already been ruled out*.

A rule-out is evidence only while the code it names is unchanged, which is why every row carries a path
and the commit it was established at. Expiry is checked with **both** `git log <commit>..HEAD -- <path>`
and `git diff HEAD -- <path>` — a red team works on an uncommitted tree, so `git log` alone cannot see
the change it is there to attack.

## Held — found once, now guarded by a test

|---|---|---|---|

## Unprobed — no oracle available

| hypothesis | path | what would settle it |
|---|---|---|
| The wait keys on `install.state`'s RECORDED uid, while `userdel` keys on the account NAME. If the account is removed and recreated by hand (or `usermod -u`'d) between install and a later uninstall, `systemctl is-active user@<stale-uid>.service` could answer `inactive` immediately (the OLD uid's manager really is down) while the CURRENT manager for that name is still live — the wait would return 0 instantly and `userdel` could race it, reopening issue #25 silently. Filed as a follow-up (owner needs to file by hand — GitHub token lacks `issues:write`, same limitation as issues #22/#26) rather than fixed here: the cleaner design (derive uid from `passwd_entry "$name"`, the live truth `userdel` acts on, instead of a persisted 3rd argument) is a bigger rework than this fix should carry mid-review | `install-lib.sh :: uninstall_host_account`, `:: wait_for_user_manager_down` | A root-capable box: install, delete the account by hand, recreate it with the same name but a different uid, then `--uninstall` — confirm whether the wait converges on the stale uid's (already-down) manager while the new one is still live |
| An unreadable/absent `systemctl` (not just a malformed uid) also produces empty stdout and burns the full timeout — same root cause class ("empty output read as down") the uid fix closed for one trigger but not this one. Filed as a follow-up | `install-lib.sh :: wait_for_user_manager_down` | A test/environment where `systemctl` genuinely can't be invoked (missing from PATH, or a non-booted systemd in a container) — confirm the function fails fast rather than polling to timeout |
| `wait_for_user_bus` (pre-existing, issue #24, untouched by this diff) has no uid-validation guard despite being the function `wait_for_user_manager_down` was explicitly modeled on. Judged lower-risk (its uid is live from `resolve_host_identity` in the same run, worst case is a loud `\|\| die`, not a silent skip) but the asymmetry between two now-explicitly-paired functions is a real gap. Filed as a follow-up, together with extracting the now-duplicated timeout-validation guard into one shared validator (the same drift-risk class that caused issue #22's duplication bug) | `install-lib.sh :: wait_for_user_bus`, `:: wait_for_user_manager_down` | Add the same `^[0-9]+$` guard to `wait_for_user_bus`, and factor the timeout-validation logic shared by both into one function |
| Real systemd behavior (`deactivating`/`inactive` state strings and exit codes) on a live, genuinely-lingering `user@<uid>.service`, and whether a real `--uninstall` against a real `dchost`-style stuck account actually converges within the default timeout | `install-lib.sh :: wait_for_user_manager_down`, `:: uninstall_host_account` | A root-capable box with GDM: reproduce the original issue's exact repro (autologin, active session, `--uninstall` immediately) and confirm the wait converges and `userdel -r` succeeds on the first attempt |
